2. EL HUECO, MEDIDO
================================================================================

En el universo la química no viene de una escena de clase: viene de la detección
que el cliente ya hace al construir. Y eso devuelve esto:

    BondDTO  { beginAtomId, endAtomId, order }     <- sin kind, sin negativeEnd
    AtomDTO  { id, element, x, y, z }              <- sin en, sin charge

Es decir: `/detection/molecule` NO devuelve electronegatividad ni tipo de enlace.

CONSECUENCIA CONCRETA: abierta desde el universo, la pantalla mostraría hoy solo
la capa de SÍMBOLOS. Las otras dos saldrían apagadas y atenuadas, que es lo que
el cliente hace cuando una molécula no trae el dato.

Y ES EL MISMO HUECO QUE EL DEL DIARIO, que tú ya identificaste: su estructura
tampoco lleva esos cuatro campos.

3. DÓNDE PONERLO: LA ÚNICA DECISIÓN
================================================================================

Hay dos sitios donde cabría, y no dan igual.

  (a) EN /detection/by-smiles          <- RECOMENDADO
      Es lo que ya prometiste en tu §C.1. El cliente pide la química por SMILES

      La química llegaría junto con la detección que el cliente ya hace, sin

POR QUÉ (a), Y NO (b):

  /detection/molecule ES CAMINO CALIENTE. Se llama CADA VEZ que la estructura
  cambia, una petición POR GRUPO de átomos, con un tope de 120/min por usuario
  que tú mismo avisaste que se acerca más rápido de lo que parece. Engordar esa
  respuesta hace más caro lo que ocurre CONSTANTEMENTE para servir algo que
  ocurre RARA VEZ: abrir la explicación es un gesto deliberado, no un efecto de
  construir.

  /detection/by-smiles es lo contrario: se llama una vez, cuando hace falta, es
  química de catálogo, no lleva token (tu §C.4) y por tanto es cacheable.

  Y cierra TRES puertas con UN cambio: el diario, el universo, y cualquier sitio
  futuro que quiera explicar una molécula. La pizarra ya no lo necesita.

  El coste del viaje extra es un toque del alumno, no un frame.

4. LO QUE HACE FALTA, LITERALMENTE
================================================================================

Lo de tu §C.1, sin cambios:

    GET /api/detection/by-smiles?smiles=O

    "structure": {
      "atoms": [ { "type": "O", "position": {...}, "en": 3.44, "charge": 0 } ],
      "bonds": [ { "beginAtomId": 0, "endAtomId": 1, "order": 1,
                   "kind": "polar", "negativeEnd": 0 } ],
      "structure2d": { "atoms": [ {"x":0.50,"y":0.50}, ... ] }
    }

  - MISMOS NOMBRES Y TIPOS que en la escena de clase. El cliente ya tiene el
    renderizador escrito contra esa forma; si los nombres cambian, hay que
    escribir un segundo y acabarán divergiendo.
  - `negativeEnd` es el ÍNDICE del átomo con δ−, o -1. El cliente lo compara con
    los dos extremos del enlace, así que un booleano no vale.
  - `structure2d` con la paridad de índices que acordaste: atoms[i] de la 2D es
    el mismo átomo que atoms[i] de la 3D.

DATO QUE QUIZÁ NO SABES: el cliente NUNCA ha llamado a /detection/by-smiles. Solo
lo conoce porque el diario incrusta ese mismo detalle. O sea que esa llamada hay
que escribirla de cero de este lado — lo cual está bien, pero significa que no
hay código viejo que dependa de la forma actual de esa respuesta. Si te conviene
cambiarla, este es el momento sin coste.

6. CÓMO SE COMPRUEBA
================================================================================

  1. GET /api/detection/by-smiles?smiles=O devuelve `en` en los átomos y `kind` +
     `negativeEnd` en los enlaces.

  5. structure2d.atoms tiene la MISMA longitud que structure.atoms.
